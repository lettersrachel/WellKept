# WK-DEV-010 v1.1 · Feasibility and Operating Leverage: Unified Implementation Directive
24 August 2026 · Supersedes the standalone feasibility brief and the v1.0 incorporation as the single developer-facing document (both filed as lineage). Adopted under the standing two-key software authorization; register A575. Figure-free; enters docs/. Reads with WK-DEV-006 (discipline and escalation), WK-DEV-007 (build authorization, input-spine standard, client freeze), WK-DEV-008 (workload evidence), and WK-DEV-009 v1.1 (attention layer, Tier D/M split). Where documents overlap, the prior directives govern; this one implements.

## 0. Feasibility verdict and the governing instruction
The expanded vision is feasible as a SMALL SET OF REUSABLE PRIMITIVES AND PROJECTIONS, never as dozens of independent feature modules. Everything requested is conventional engineering: relational state, purpose-based permissions, workflow events, background jobs, secure links, read models, AI-assisted extraction. The hard part is discipline: semantics, privacy, frontline burden, evidence quality, controlled authority. The governing instruction, now doctrine: **build boring infrastructure underneath unusually thoughtful household operations.**

## 1. The operating-leverage test (every RFC answers all seven)
Every meaningful change must increase useful capability, improve quality/safety/reliability/scalability of an existing capability, or materially reduce unnecessary human burden; the best do several. The RFC template requires all seven answers: Functionality (what can Well Kept reliably do after this that it could not before); Client value (more handled, anticipatory, coordinated, confident); Cognitive load (which noticing, remembering, interpreting, deciding, planning, coordinating, monitoring, verifying, or retriggering work is removed, and from whom); Operational value (whose work gets easier, safer, more consistent, more scalable); Quality and learning (what the system learns or verifies that it could not); Maintenance tax (section 2's estimate); Reuse (which shared primitive it builds on or extends, never duplicates).

## 2. Maintenance-tax control (a design input, never an afterthought)
The maintenance tax is the recurring cost of keeping a feature correct, usable, trained, integrated, supported, and safe after launch. Six taxes, each with its required mitigation, stated in every RFC:
- Human: repeated HOM fields, client approvals, corporate review, vendor education, manual cleanup → derive, prefill, batch, exception-only input, standing rules, role-specific surfaces.
- Technical: custom services, one-off integrations, feature-specific alerts → shared primitives and adapters; configuration before custom code.
- Data: facts that stale, expire, conflict → freshness state, provenance, review dates, supersession, automatic expiry.
- Training: manuals drifting from production → version-linked contextual guidance and TrainingState (section 10).
- Support: repeated where/how/what-happened questions → contextual search, verified knowledge, stable mental models.
- Vendor/integration: changing APIs → adapters behind interfaces, the dependency ledger, the 3P-01 review process.

## 3. Canonical domain model
Semantic objects (physical tables only after reconciliation with the existing schema; extension tables over new near-duplicates): Household → HouseholdTaskProfile, PreferenceRule, KnowledgeFact, Asset, ParticipantRelationship, WorkRequirement, EstimateSnapshot, ServiceEvent, BriefSnapshot, OutcomeVerification, DecisionRecord, AttentionRecord, ExecutionEvent, ClientTouchEvent, LearningCandidate. ExternalParticipant → IdentityAccessGrant → PurposePack. User → role → TrainingState.

**Work boundaries, memorized:** a Task Definition is reusable work semantics; a Household Task Profile is how that task manifests in one household; a Work Requirement is a date/context-specific instance that can be scheduled, blocked, completed, verified; a Service Event is an appointment/visit interaction that may fulfill one or more Work Requirements and involve external parties; a Task Occurrence records what actually happened and NEVER overwrites the original estimate snapshot. These align one-to-one with WK-DEV-008's objects; build once, in the substrate window, to the standard definition of done.

## 4. Event law
The event substrate is the primary technical prerequisite for operating leverage. The pipeline: authoritative write transaction → database state change → durable outbox event IN THE SAME TRANSACTION → idempotent worker drain → projection refresh → attention routing → QA metrics → forecast recompute where applicable → LearningCandidate detectors → integration adapters. Requirements: every material event carries event_id, event_version, correlation_id, object_id, household_id where applicable, actor, timestamp, sensitivity, and provenance; events describe STATE TRANSITIONS, never copies of full records; consumers are idempotent and retries never duplicate appointments, notifications, approvals, invoices, or follow-ups; history is append-oriented and corrective events supersede rather than mutate; business rules live in Well Kept services, never in consumers. This extends, never duplicates, the covenant-event spine (visit_arrival, visit_departure, household_departure + cause_code) and WK-DEV-009's seven event families.

## 5. ServiceEvent: full specification
Logical fields: id, household_id, service_event_type, work_requirement_ids[], case_id/runway_id (nullable), asset_ids[]/zone_ids[], provider_org_id (nullable), provider_participant_ids[], hom_id, scheduled_start/end, arrival_window, status, scope_summary, requested_outcome, authority_snapshot_id, access_instruction_refs[], relevant_history_refs[], source_refs[], evidence_refs[], estimate_refs[], invoice_refs[], provider_submission_id, hom_verification_id, outcome_state, follow_up_requirement_ids[], sensitivity, created/updated/closed_at, correlation_id.

Lifecycle: CREATED → CONTEXT_READY → CONFIRMING → SCHEDULED → ARRIVAL_PENDING → IN_PROGRESS → PROVIDER_SUBMITTED → VERIFYING → RESOLVED | NOT_RESOLVED | DISPUTED | FOLLOW_UP_REQUIRED → CLOSED; any closed issue may → REOPENED. One shared lifecycle with type-specific extensions is the adopted default shape (dispositioned decision, section 12); propose deviations per the escalation clause.

**Brief snapshots:** every projection shown to a HOM, vendor, or member persists as an immutable snapshot (references, version identifiers, rendered summary; never a new authoritative copy) so corporate can reconstruct exactly what anyone saw at any point. Future briefs regenerate on state change; historical snapshots never rewrite. Every projection applies the server-side permission and sensitivity filter BEFORE any AI summarization touches it.

**Same truth, different visibility (the projection doctrine, with the brief's own example):** canonical fact "child naps 12:30-2:30, quiet rule" renders to the HOM as reason plus operational implication; to the vendor as "do not ring; text the HOM"; to the member as confirmation the vendor received quiet-arrival instructions, if useful. A prior vendor-reliability concern may show internally when operationally needed, NEVER to the vendor, and to the member only if it becomes decision-relevant. Standing repair authority shows the HOM the exact boundary, the vendor only the approved scope, the member only whether their decision is needed. This table pattern is the acceptance standard for every projection built.

## 6. The vertical slice: vendor repair, detection to verified resolution
The architecture's proving ground, first major workstream after the HO sprint's green go/no-go. Stages, each an acceptance line:
1. Detection: member or HOM reports (via Tell Well Kept or intake); Work Requirement created/activated with provenance.
2. Context assembly: asset, prior Service Events, warranty, preferred vendors, access and quiet rules, Decision Rights linked automatically.
3. Vendor selection/authorization: existing preference and authority rules applied; a genuine member decision creates exactly one DecisionRecord.
4. ServiceEvent creation binding vendor, HOM, asset, requirement, window, and an authority snapshot.
5. Previsit projections: HOM Previsit Brief, Vendor Work Brief, Member Visit Preview generated from ONE canonical state (the member preview lands in the digest per the client freeze).
6. Vendor participation via the secure link: confirm, ETA, scoped context, upload estimate/report/photos, mark ready for verification. **Ruling in force: internal simulation only** until the external security test covers the link surface; founder or developer plays the vendor on staging against synthetic data; the pen-test scope document gains this surface now.
7. During visit: HOM operates from Visit Mode; novel conditions through Tell Well Kept; new scope creates a DecisionRecord, never informal approval.
8. Provider close: vendor submits structured or unstructured; extraction [M-gated] or manual transcription until Tier M opens.
9. HOM verification: independent outcome check. **Vendor-complete never implies resolved**; a failing check with a vendor claim of completion lands in DISPUTED with both observations preserved.
10. Client outcome summary in the digest; follow-up requirements spawn; QA and learning events emit downstream.
Slice acceptance: the full flow runs end to end on a synthetic household, every projection passes the section 5 visibility standard, the disputed path works, and every stage emitted its events into the projections, dashboards, and (shadow) learning detectors without any feature-specific side channel.

## 7. External access law: ExternalParticipant, IdentityAccessGrant, PurposePack
Person, relationship, account, and authorization are DISTINCT. ExternalParticipant (identity, contact, household relationships) implies no access. IdentityAccessGrant is the only source of access: participant, household, purpose pack, object scope, capabilities, validity window, auth strength, granted-by and reason, revocation with reason, audit refs. Rules, all binding: relationship never implies permission; role names are presets, capabilities and scope are authoritative; occasional vendors need no account or app install; every grant expires automatically or carries explicit review (per-event links expire at event close plus a short grace; standing grants at most 90-day review); emergency revocation is one corporate action killing every grant for a household, tested like a kill switch; a vendor link is scoped to its event and permitted actions only and CANNOT enumerate the household, other events, internal notes, or unrelated documents; deny paths and cross-household isolation are release-blocking tests. Elevated defaults from the incorporation: household-private data transforms into operational instructions rather than being revealed, and no raw S2/S3 content is EVER projectable to an external participant; changing that is a register-visible founder decision. Purpose Packs, in build order on operating need after the slice proves reuse: Vendor Visit first; then Household Delegate, Household Staff, Sitter/Pet Care, Professional Project, Emergency Delegate; each pack's first real grant recorded in the weekly note.

## 8. Client cognitive-load telemetry (backend-only)
ClientTouchEvent (household, source object, touch type, required_response, necessity: necessary | avoidable | unknown, reason code, timestamps) and OwnershipTrace (who noticed, planned, decided, executed, verified, retriggered) are adopted. Avoidable-touch reasons, verbatim: missing knowledge, stale knowledge, retrieval failure, repeat question, unnecessary approval, software workflow defect, vendor preventable exception, duplicate communication, unclear authority. A maturing household should need fewer avoidable touches and fewer repeated decisions; this is a product-quality signal, never a client-engagement target, never a household score, never member-visible without its own release decision, corporate-only in the permission matrix.

## 9. Dashboards consume, never collect
Corporate dashboards build only on events already emitted by normal workflow (Operating Health: which households need intervention before quality is felt; Capacity and Forecast per WK-DEV-008; the exception and covenant views per WK-DEV-007 section 5). Any dashboard that would require new frontline data collection is redesigned at the capture side per the attention ladder, not shipped.

## 10. Training as an application layer
TrainingState per user, role, and workflow: not_introduced | introduced | practiced | verified | refresher_needed | changed_since_training, with trained workflow and standard versions, practice and verification records, help-request count, last use. Version links make training drift detectable: when a workflow ships a breaking change, affected users flip to changed_since_training automatically and the release checklist says who needs what. **The Training Household** is a permanently seeded synthetic household that behaves like a real one and contains, deliberately: realistic room and asset records; a standing decision and one decision OUTSIDE authority; a vendor appointment and a late vendor; access and quiet constraints; a stale household fact; an offline visit; an intentional AI misclassification [stubbed until Tier M]; a normal close and a disputed outcome; a safety exception; a backup-HOM scenario. February training runs on it; so does every future hire and the demo instance. **Training rule, binding: never train around product defects.** If several competent users struggle with the same workflow, investigate UX, validation, data, and workflow design BEFORE scheduling retraining.

## 11. The operating-leverage scorecard
Definition: as households and complexity grow, human coordination, reconstruction, checking, and administration grow SLOWER than service delivered. Measured per area, reported in the weekly note as the layers land: HOM (admin minutes per visit, manual fields per normal visit, searches for known facts, close-flow time, duplicate entry, interruptions, AI corrections); Client (avoidable touches, repeated questions, unnecessary approvals, status-check messages, decisions converted to standing rules); Vendor (coordination touches per event, missing-information reschedules, duplicate requests, diagnosis-to-decision time, callbacks); Corporate (manual exception reviews, founder interventions, recurring root-cause categories, support contacts, unresolved data-quality issues); Product (percentage of updates derived or prefilled, useful downstream outputs per human input, workflows reusing shared primitives vs custom paths).

## 12. Decisions: answered, ruled, or clocked
Answered from existing work: platform per workflow (the eighteen-workflow SoR map, PR #119; Jobber and processor per Ruling 2a); outbox existence (verified at Gate 0; CAND-OUTBOX-01 week one); AI confirmation governance (handoff section 14 plus the batch ruling as unified in WK-DEV-009 v1.1); dashboard data availability (the Gate 0 delta report). Ruled here or in the incorporation: vendor-projectable sensitivity (operational-instruction transform, no raw S2/S3); expiry and emergency revocation (section 7); freshness-first fact classes (access, safety, location first); lifecycle shape default (one shared lifecycle, type extensions); calibration-first families (corporate selects after HO's first month, weighted by importance); process-mining and predictive thresholds (later-with-evidence, ADR when proposed); early vendor integrations (evidence-gated on HO and the first real households). On the 48-hour propose-default clock: no-app link authentication (expected shape: short-lived signed link plus a per-event verification factor, no account).

## 13. Anti-patterns (each with its required alternative, enforced in review)
Feature-specific schemas everywhere → shared domain objects with extension tables. Native vendor app now → scoped secure web link. Every state change notifies → AttentionRecord plus routing policy. Every AI result fully reviewed → confidence times consequence. High confidence means autonomous → authority always constrains AI. Universal task stopwatch → selective CalibrationAssignment. Client dashboard mirroring internal ops → the calm anti-dashboard, decisions and outcomes only. "Many users struggle, so retrain" → investigate the product first (section 10's rule). Vendor-complete equals resolved → independent verification, disputed path preserved. Relationship equals access → explicit scoped grants only.

## 14. Testing and acceptance matrix (release-blocking unless noted)
Tenant isolation: cross-household read/write attempts across member, HOM, corporate, vendor link, delegate, collaborator roles. Purpose-limited vendor access: the link cannot enumerate anything beyond its event. Grant expiry/revocation: expired or revoked access denies immediately; session handling per policy. ServiceEvent projections: the same event renders correct HOM/vendor/member/corporate views with classified data excluded, per the section 5 table. Disputed outcome: vendor-complete plus HOM-failing cannot close resolved; both observations preserved. Offline HOM: previsit context, capture, exception, and close remain safe offline with ordered idempotent sync. AI extraction [when Tier M opens]: source ref, confidence, and correction path retained; consequential fields require review (blocks the affected AI flow, not the release). AI containment: authority caps and kill switches verified per WK-DEV-007 section 3.
