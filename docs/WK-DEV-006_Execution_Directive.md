# WK-DEV-006: Execution Directive
Version 1.0 · 24 August 2026 · Adopted under the two-key software-updating authorization of 24 August 2026 (register A567 draft; transcription into WK-QA-018 pending)

## 0. What this document is
The decision-complete build directive. Read order for the developer: 00_CURRENT_AUTHORITY.txt, then this directive, then the Implementation Handoff (2026-08-24, including section 24), then WK-DEV-001..005 as the controlled detail. Where this directive resolves something the handoff left open, this directive wins, and the resolution carries its authority citation. The intent is explicit: after this document, the only external engagement this build requires is security testing. Every design question is answered here or in a cited controlled document; anything that is not is a defect in this directive, raised through the escalation path in section 8, never solved by hiring another consultant.

## 2. Build phases with acceptance criteria
Phases are the handoff's sequence made concrete. A phase is complete when every acceptance line passes and the Definition of Done (handoff section 18) holds for each shipped surface.

**Phase 0 · Truth (target: 1-2 weeks).** Deliver: VERIFIED AGAINST REPO delta report on WK-DEV-003; REQ-078..082 appended verbatim from INSTRUCTION_UPDATES_2026-08-05_v2; monthly stack run-rate statement (REQ-085); per-workflow system-of-record map documenting D1; owners and dates on every surviving section 22 CAND (24.7); demo-to-commitment ledger verification tags resolved (24.5). Acceptance: the full current test suite runs green locally and in staging before any change; every stack row carries a verified status; run-rate is within the modeled software line or a two-key exception is filed first.

**Phase 1 · Custody and security (before any real household data).** Deliver: WK-SEC-001 white-box audit executed on staging with synthetic data and remediations filed; LLC ownership confirmed on GitHub org, hosting, database, object store, and every billing account (24.8); passkey MFA live for privileged accounts (D3); tested backup restore; incident and rollback runbooks; brief-08 mappings closed (data inventory, access matrix, retention schedule per REQ-077, deliverability webhooks); custody audit by a second qualified developer against the handoff section 20 artifact list. Acceptance: restore drill performed and timed within RPO/RTO (REQ-072); a simulated developer-offboarding executes cleanly from the account matrix; zero criticals open from WK-SEC-001.

**Phase 2 · Launch substrate (production-ready before February 2027 training).** Deliver, and nothing more (handoff 24.2): the Household Record with ingest of the paper intake, including an importer path from HZ_Live_Household_Record_Master via the existing tooling/import package; intake flow with ACH mandate capture against the D5 abstraction; the weekly digest; arrival/departure event capture (`visit_arrival`, `visit_departure`, `household_departure` with `cause_code`) feeding payroll AND the REQ-083 covenant report; the trainee role (D6); the client anti-dashboard shell honoring D7. Acceptance: a full synthetic household runs intake, four weekly cycles, one digest per cycle, one simulated departure with cause code; the monthly covenant report generates as a pure function of events and matches a hand computation; the D7 lint passes across every client route; the founding HOMs can run their February training entirely on these surfaces.

**Phase 3 · Operating hardening (during the 2027 ramp, evidence-gated).** Ordered strictly by operating evidence, not by roadmap enthusiasm: notification/attention budgets (handoff section 10), Desk triage with SLA clocks (manual triage, logged clocks, per 24.5), corporate dashboard reads, then and only then the anticipation surfaces of WK-APP-002 as real playbook data accumulates. Acceptance per feature: the handoff's Definition of Done plus a named operating trigger recorded in the ADR ("built because X happened," never "built because it was next").

## 3. Sole external engagement: security testing
One engagement, scoped now so it cannot creep into development consulting: an independent penetration test and audit review against WK-SEC-001 scope, executed at the end of Phase 1 and repeated before real member data exceeds three households. The tester receives: the WK-SEC-001 scope document, the threat model, staging access with synthetic data only, the permissions contract matrix, and the account matrix minus secrets. The tester delivers findings and severities; the developer remediates; nothing in the engagement authorizes architecture or feature advice, and any such advice routes through section 8 as a CAND, not into code. Budget the annual pen-test line item already carried in REQ-070.

## 4. What the developer never builds (standing walls)
No property-data enrichment of any class (REQ-084, CI-enforced). No client-surface time quantities (D7). No card acceptance without a two-key re-cost. No select-all or batch AI approval; the single-consent rule stands (handoff section 14). No third-party analytics on the client portal (REQ-071). No feature from any document in 99_ARCHIVE_superseded or carrying a STATUS_NOTE. No spend above the modeled software line without a prior two-key exception (REQ-085).

## 5. Fixtures and test data
Synthetic only until Phase 1 clears: the Fernbrook demo family and the seeded sample playbooks are the fixture set; extend them rather than inventing new synthetic households. Household Zero's real record enters only through the Phase 2 importer, after Phase 1, as the first production ingest, and is treated as member data from the moment it lands.

## 6. Reporting cadence
A one-page weekly build note to the founder: phase, acceptance lines passed, run-rate vs budget, blockers with age. Any blocker older than one week gets a register-visible note. The covenant report (REQ-083) is demonstrated monthly from Phase 2 onward even with synthetic data, so the first real lender submission is the tenth run of the report, not the first.

## 7. Open items that are the founders' to close (the build does not wait on them)
The dues display unit (D4 proceeds unit-agnostic). Processor selection from the D5 shortlist (48-hour turnaround committed). The training two-track doctrine ruling (D6 serves either outcome). The Founding Credit ruling and model-variant adoptions (no product surface depends on them).

## 8. Escalation
Design questions this directive fails to answer go to the founder in the weekly note or sooner, with a proposed default; the founder answers within 48 hours or the proposed default stands and is recorded as an ADR citing this clause. Requirement changes route through WK-DEV-001 with register discipline. Nothing is ever resolved by engaging additional development consultants; that path is closed by design, and this clause is the reason the directive is as long as it is.
