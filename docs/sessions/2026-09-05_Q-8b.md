# Session · 5 September 2026 · Q-8b, the provider-independent export

Queue item Q-8b under the standing authorization. **Authority: the
intaken portability line** (`docs/intake/2026-09-03-build-package/BENCHMARK_ADOPTION.md:18`),
plan-of-record. The row's REQ-017 citation was corrected before this
session started (G-122); REQ-017 is a different deliverable and is now
Q-11p.

Migration: **none**, and unlike Q-6 that is checked rather than assumed.
An exporter reads and an importer writes existing tables; the only
candidate for new state would be a record that an export happened, and
`audit_event` already carries that.

## Plan, written before code

### The table set is COMPUTED, which is the whole design

The acceptance says the archive "restores a COMPLETE household". A
hand-written list of tables cannot make that claim for longer than it
takes someone to add a table: the list would still pass its own tests
while the archive silently stopped being complete. So the exporter
introspects the schema at runtime for every table carrying a
`household_id` column (43 today, computed, plus the `household` row
itself), and **everything is IN by default**. Each exclusion is a
written entry, and a new table joins the archive automatically or fails
the guard.

This is the G-78 posture pointed the other way. There, the danger was a
new column reaching a member by default and the answer was an explicit
allow-list. Here the danger is a new table NOT reaching an archive that
claims completeness, so the default inverts and the written list is the
deny side.

### Three exclusions, each with its reason

1. **`vault_item`: EXCLUDED.** The authorization is explicit that S3
   values enter only under a separate authorized reveal and never in
   the default archive. Excluding the ciphertext rather than merely
   declining to decrypt also means an archive is not an offline attack
   surface against the vault.
2. **`audit_subject_token`: EXCLUDED.** It is the ADR-006 mechanism
   whose DELETION is how audit identity is erased, and it maps tokens
   to people including STAFF addresses, which are the company's and not
   the household's. The audit trail itself exports whole with its
   tokens intact, so the record of what happened is complete; what a
   restored archive cannot do is dereference a token to a person, which
   is the correct loss and is stated in the manifest rather than left
   to be discovered.
3. **`visit_photo`: PROJECTED, not excluded.** Photo bytes live in the
   database; the portability line asks for a "document and media
   MANIFEST" in its own words. So the archive carries one row per photo
   with its identity, visit, uploader, size and content hash, and not
   the bytes. The hash is what makes it a manifest rather than a list:
   a restored archive can prove which photo a row refers to if the
   bytes are supplied separately.

### REPORTED, and the reason it cannot be settled inside this item

**The archive is CORPORATE-COMPLETE, and whether a MEMBER receives the
same set is undecided.** The freeze split makes that safe today: no
member-facing control ships, so generation is a corporate act. But the
freeze-gated control is one ruling away from shipping, and if it ships
over this archive it hands a member several things the rest of the
system deliberately withholds from them:

- `paused_decision`, whose own table comment reads "INTERNAL: no client
  projection exists at all" and whose payload guard treats any
  recognizable row in a client payload as a violation;
- `shadow_log`, internal engine output;
- `capture_artifact`, the HOM's pre-filing words;
- `decision_right`, whose member surface is itself freeze-gated, and
  which this repository added a payload signature for four commits ago.

The portability line's own list does not name any of them: it says
canonical structure, media manifest, vendor, asset, work and outcome
history, preferences and standing rules, access history and audit
metadata. So the member-scoped subset is a DIFFERENT set from the
corporate archive, and nobody has decided it. **That decision belongs
with the freeze lift and not to this session**, and it is reported here
so the 25 September ruling is made knowing the export exists and would
carry everything unless scoped.

### What ships

- `pnpm db:export-household --household <uuid> --out <file>`: a corporate
  act, refusing without both arguments. Writes a JSON archive with a
  manifest (schema version, migration count, generated-at, the table
  set, the exclusions and their reasons, per-table row counts).
- `pnpm db:import-household --file <path> --as <uuid>`: restores into a
  CLEAN household id, refusing to overwrite an existing household, so an
  import can never silently merge into a live tenant.
- Round-trip proof: export a fixture household, import it as a new id,
  compare per-table row counts and content, and assert parity.

### Deliberately NOT in this session

- The member-facing control (freeze-gated, and the scoping question
  above is unanswered).
- S3 reveal into an archive. It is a separate authorized act by the
  authorization's own words; nothing here decrypts.
- Photo bytes. The manifest is what the portability line asks for.

## Built and proven

**The export half is BUILT and works.** `pnpm db:export-household` wrote
a real archive from Fernbrook Demo: **41 tables, 553 rows, migration
count 67**, with the two exclusions named in its own manifest. Both
refusals proven first (no arguments; an unknown household).

**The S3 rule is proven BY THE ARCHIVE'S CONTENT, not by a claim.**
Reading the written file back: `vault_item` absent, `audit_subject_token`
absent, `visit_photo` present as 44 manifest rows carrying
`content_sha256` and **no `data` key at all**, and the three known losses
stated in the manifest.

**Two red proofs on the design assertions**, each mutation confirmed
landed: dropping a household-keyed table from the set without a written
reason fails naming it; reverting the photo projection to a keep-list
fails on the rule that a projection names what it drops.

**The projection assertion earned its keep on its first real run.** The
first version used a hand-written KEEP list and was wrong about three
`visit_photo` column names; the assertion refused rather than silently
writing a short manifest. Inverting it to name the one DROPPED column
fixed the immediate error and removed the drift shape: a column added to
`visit_photo` tomorrow now stays in the manifest instead of falling out
of a list nobody updated.

**The importer carries two structural refusals, both proven:** it will
not write into an existing household (an importer that merged into a
live tenant is a data-loss tool wearing a restore tool's name), and it
refuses a migration-count mismatch at the door rather than failing
somewhere in the middle with a confusing column error.

## REPORTED AND BLOCKING: the archive is not self-contained, and closing it is a founder decision

**The round trip was RUN, into a genuinely clean instance** (a separate
database migrated to the same count, because the acceptance says "a
clean instance" and restoring into a new household id in the SAME
database collides on preserved row ids, which the first attempt proved
by refusing on `attention_record_pkey`). It refused again, and rolled
back cleanly, on a foreign key: `condition_flag_raised_by_auth_user_id_fk`.

**The measurement, not an impression.** Foreign keys from the archive
set pointing outside it:

| Points at | Foreign keys | From |
|---|---|---|
| `auth_user` | **38** | 26 of the 41 archived tables |
| `task_definition` | 1 | `household_task_profile` |

**And nulling the people is not available:** of those 38 person columns,
**20 are NOT NULL** and 18 are nullable. So "export the household and
drop the references" fails on twenty columns; that is a fact about the
schema rather than a preference.

`task_definition` is uncontroversial and would simply join the archive:
it is global reusable work semantics with NO member data by its own
design.

**`auth_user` is the decision, and it is not an engineering one.** The
table is `id, name, email, email_verified, image, is_tester`. So a
self-contained archive of a household contains **the names and email
addresses of every HOM and corporate person who ever touched that
household's record**. This system already treats audit identity as
something to TOKENISE rather than export (ADR-006, and the reason
`audit_subject_token` is excluded above), so shipping people wholesale
inside the archive would run the other way from a decision already made.

**Three shapes, with what each costs:**

1. **Include the referenced `auth_user` rows whole.** A true restore,
   byte-for-byte. Exports staff names and addresses with the household's
   record, and does it into an artifact whose member-facing control is
   one ruling from shipping.
2. **Include a PSEUDONYMISED people table**: the referenced ids with a
   role label and no address, enough to satisfy every foreign key. The
   restore is structurally complete and a reader can tell that two
   different people touched a row without learning who. This is the
   ADR-006 posture applied to the archive.
3. **Include the household's OWN people whole and pseudonymise staff.**
   The member gets their own identities back intact and the company's
   people stay tokens.

**I am not choosing among them**, because the choice decides whether
staff email addresses travel inside a household's exported record, and
because the export's member-facing half is freeze-gated with the
scoping question below still open. Shape 2 is the one that matches the
posture already in the tree; that is a reading, not a ruling.

## Also reported, unchanged from the plan

**The archive is CORPORATE-COMPLETE and the MEMBER-scoped subset is
undecided.** It currently carries `paused_decision` (whose own table
comment reads "INTERNAL: no client projection exists at all"),
`shadow_log`, `capture_artifact` and `decision_right`, none of which the
portability line names and each of which another mechanism deliberately
withholds from members. Safe today because generation is a corporate
act; **the 25 September freeze ruling should be made knowing that the
export exists and would carry all of it unless scoped.**

# The three rulings, applied (5 September 2026)

The founder ruled the blocker and two other things in the same message.
Recorded here in her order.

## Ruling 1: people are pseudonymised (shape 2)

Adopted as given. The archive carries a `people` array of `{id, role}`
and nothing else, and the restore writes `auth_user` rows with a NULL
name and an address under the RFC 2606 reserved `.invalid` TLD, which
is visibly not an address and can never route. Her reasoning is
recorded in the module: staff names and addresses do not enter an
artifact whose member-facing control is one ruling from shipping, and
the tree already tokenises audit identity. Shape 3 is noted as right in
principle and needing a rule for who counts as the household's own
person, which does not exist.

**The role is NULL when the person holds no role on this household.**
Not "staff", because coining a label would be choosing a vocabulary,
and NULL is the true statement that this person touched the record
without holding a role on it. **This shape was exercised on real data
rather than reasoned about:** a person who reaches the archive only
through a global row's `created_by` restores with `role: null`.

**The person set is COMPUTED from the schema's own foreign keys**, not
from a column list. A hand list goes stale and the restore then fails
on the key it forgot, which is exactly how the first round trip failed.

## Ruling 2: `task_definition` joins the archive

Adopted, with one narrowing stated rather than assumed: **only the
REFERENCED rows travel**, reached through `household_task_profile`'s own
column, because a household's archive is not the place to ship the
company's entire reusable work catalog and the FK closure needs only
what is pointed at. Proven on real data: with two definitions referenced
out of four in the store, the archive carried exactly two.

## Ruling 3: the export takes an explicit scope

`--scope corporate|member`, **required, no default**, because a default
would be this session choosing which of two audiences an archive is for.

**The two scopes run their defaults in opposite directions, and that is
the design.** Corporate fails by being incomplete, so everything is in
and the written list is the deny side. Member fails by handing a
household internal material, so nothing is in and the written list is
the allow side. A table added tomorrow therefore joins the corporate
archive automatically and the member archive never, until someone names
its portability category in a reviewed change.

**The member allow-list is deliberately SMALL, and this is the part
that needs review.** Her ruling names four tables to exclude and then a
rule, and applying that rule across forty-one tables is a taxonomy
exercise. Rather than invent one, the list admits only tables something
else already decided are member-visible, six today, each naming the
portability phrase that admits it. **The categories that are
consequently EMPTY, and what blocks each, are in the freeze packet**
(`docs/FREEZE_DECISION_PACKET_2026-09-25.md`), because they are exactly
what the 25 September decision should be made knowing.

**A row-level half that a table-level rule would have missed:**
`playbook_field` is member-visible and its s2 rows are not. The member
scope filters to `sensitivity = 's1'`. Without it the member archive
would have carried 21 s2 rows and 7 s3 field rows, measured by running
the exporter with the filter removed rather than by reading the code.

## The restore half is FINISHED

**The round trip runs clean into a genuinely clean instance.** A
separate database migrated to 67, corporate archive restored as a new
household id, then verified by query against the archive's own manifest:
**41 tables compared, zero row-count mismatches**, the single difference
being the 44 photo manifest rows, which are the stated loss.

**Two things the finished restore needed that the plan did not
anticipate.**

1. **The insert ORDER is computed, not listed.** The archive's tables
   reference each other, and alphabetical order breaks on the first such
   pair. The importer now reads the foreign keys among the carried
   tables from `information_schema` and topologically sorts them, so a
   table added tomorrow orders itself; a cycle refuses with a message
   naming the tables rather than failing halfway.
2. **A self-reference is deferred by nulling ONE nullable column of the
   constraint, and finding that out cost a real failure.** The first
   version nulled every column of a self-FK and died on
   `event_outbox.household_id`, which is NOT NULL: the causation key is
   the COMPOSITE `(household_id, causation_id)`, so grouping by column
   rather than by constraint had no way to pick the right one. Grouping
   by constraint is what makes the choice available. **The path is
   exercised on real data, not by sentinel:** a real causation chain was
   written into the fixture, exported and restored, and read back as one
   restored chain.

**The photo rows are NOT restored, and that is a decision this session
made rather than a fact it found.** `visit_photo.data` is NOT NULL, so a
restore either inserts a placeholder or skips the rows. A placeholder
would write a row claiming a photo with empty bytes, which is a claim
rather than a gap, so the rows are skipped and the known-loss text now
says both halves plainly: the archive file records which photos existed,
the restored database does not carry them. **Reported as a choice**, in
case the other one is wanted.

# The acceptance rulings, applied (5 September 2026, after the merge of #299)

## Ruling 1: the allow-list is TOTAL over the corporate table set

Built. `CORPORATE_ONLY` now carries a written reason for every table in
the corporate archive that is not in `MEMBER_SCOPE`, and the guard
fails on a table with no entry rather than letting it default quietly.

**Her framing is the reason it is worth the length:** leaving a table
out now requires writing it down, so "considered and left out" leaves a
trace. Before this, that state and "never considered" were the same
absence, which is exactly what the note at the end of the last section
said could not be caught. It can, and the mechanism is the
erasure-coverage floor applied to a second question.

**The reasons are grouped by the rule that holds each table out**, not
by table, because the groups are the actual decision: the anticipation
engine's own bookkeeping, staff-authored internal records (four of
which `legal/README.md` says in as many words are never shown to the
client), duration-carrying tables held by D7, delivery plumbing, money
under R25, the founder-named four, and the one held on the stricter
reading of a live conflict.

**`client_edit` is named in its own reason as the nearest candidate for
admission of anything on the list**, since it is half the member's own
words and half an internal review disposition. Recorded there rather
than in the packet, because it is not a freeze question.

**Three red proofs, each mutation confirmed landed first, green
restored after each:** a table's decision removed (fails naming `dot`
and telling the author which list to add it to); a decision written for
a table excluded from every scope (fails as stale, the reverse
direction); and a table decided BOTH ways (fails as contradictory).

Eighteen cases in `household-archive.test.ts`.

## Ruling 2: the four empty categories become rulings, not findings

`docs/FREEZE_DECISION_PACKET_2026-09-25.md` now states three rulings,
each with its shapes, framed to be answered in a sentence. Four
categories, three rulings, because work history and outcome history are
one decision.

- **A. Do a visit's HOURS reach a member archive, and in what shape?**
  Three shapes: D7 holds and visits stay out; visits travel with the
  duration keys projected out; visits travel whole. The note that
  belongs with the middle one is that a jsonb key list is the same kind
  of written, reviewed list as the table list, since no guard can read
  inside a jsonb column. The note on the third is that it needs D7
  amended by name rather than interpreted, so a later session does not
  have to reconstruct whether an export counted as a client surface.
- **B. Does the media manifest ship?** The portability line names it and
  `legal/README.md` says photos never appear on the client's view. The
  distinction offered rather than assumed: a manifest row carries a
  hash and no bytes, so a member would learn which photos exist without
  receiving an image. Held on the stricter reading meanwhile.
- **C. Is vendor history satisfied by registry entries?** Flagged as
  possibly not a freeze question at all: if "vendor history" means the
  record of vendor ENGAGEMENTS rather than the vendors on the registry,
  nothing in the schema holds it and the answer is a queue item.

The packet's own framing line is corrected in the same pass: it said it
made no recommendation while one entry carried a framing note, so it now
says it does not choose an outcome and states engineering consequences
beside the shapes they belong to.

**Two hand-carried counts removed from the packet on the way** ("six
tables", "thirty-five tables"), both sitting next to the thing they
counted. The list is the count where a list is present, and the guard is
the count where it is not.
