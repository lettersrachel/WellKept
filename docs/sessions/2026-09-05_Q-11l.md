# Session · 5 September 2026 · Q-11l, the vault reveal outcome vocabulary

Queue item Q-11l under the standing authorization, on the founder's ruling of
the same day (`docs/FOUNDER_RULINGS_2026-09-05_G53_G13.md`). **One migration.**

## The row's premise is STALE, and the correction comes first

Q-11l and G-53 both read as though the reveal records only the attempt. **It
already records an outcome.** Commit `42176a9` ("Fix G-54 ... and G-53 (the
reveal records its outcome)") shipped the second append earlier in this run:
`apps/web/src/app/api/reveal/route.ts` writes a second `audit_event` of kind
`s3_reveal_outcome` after the decrypt resolves, with the two writes deliberately
not in one transaction so a failed second write leaves the conservative attempt
row standing.

So this session is a RECONCILIATION rather than a first build, and three things
are actually wrong:

1. **The vocabulary is not the ruled one.** The code writes `delivered`,
   `no_vault_item`, `decrypt_failed`. The ruling is `delivered`, `denied`,
   `not_found`, `failed`.
2. **`denied` has no producer, and the hole is bigger than a missing value.**
   The authorization refusal at `route.ts:60` returns 403 and writes NOTHING, so
   **an authorization refusal leaves no trace in the trail at all.** The trail
   can say who attempted and now what they got; it cannot say who was turned
   away.
3. **The vocabulary is not closed by anything.** It lives in `detail` jsonb, so
   a fifth value is one keystroke and no constraint objects. The ruling says the
   vocabulary is closed and a fifth outcome is a report.

## The plan

**Migration 0068, additive:** a `vault_reveal_outcome` enum carrying the four
ruled values, and a nullable `audit_event.reveal_outcome` column, with a CHECK
tying the two together: an `s3_reveal_outcome` row must carry a typed outcome
and no other row may. The vocabulary becomes closed by the database rather than
by discipline, which is what makes "a fifth outcome is a report" enforceable.

**The reasoning goes beside the enum**, by the ruling's own instruction: four
values rather than two because "who viewed this" is asked by counsel and by
members, so the answer must separate someone who SAW a value from someone who
tried and got nothing, and separate a refusal from a broken record.

**The route** writes the typed column, maps its three current values onto the
ruled ones (`no_vault_item` to `not_found`, `decrypt_failed` to `failed`; same
meanings, different words), and gains the `denied` producer: an authorization
refusal writes one outcome row and returns 403 unchanged.

**A denied row stands alone**, with no attempt row before it, and that is
correct rather than an asymmetry to fix: no decryption was attempted, so there
is nothing to have attempted. The audit invariant is untouched, because it
governs the path where a value is about to be decrypted.

## Deliberately NOT in this session

- Any change to the ORDER of the two writes, or to their non-transactionality.
  Both are load-bearing and stated in `CLAUDE.md`.
- A backfill of old `detail.outcome` values in production. Zero
  `s3_reveal_outcome` rows exist locally; whether production holds any is one
  founder-side query, and mapping historical values is a data change that
  belongs to whoever can read them.

## Built, and proven

**Migration 0068**: the `vault_reveal_outcome` enum with the four ruled values,
a nullable `audit_event.reveal_outcome`, a hand-placed backfill mapping the
three provisional values onto the ruled ones, and the CHECK. Generated SQL read
before applying; the backfill was inserted BY HAND between the column and the
constraint, because a constraint added before the rows are classified would
refuse the rows this migration is about to fix.

**Proven in SQL, with the constraint and the enum printed from `pg_constraint`
and `pg_enum` before any case ran:**

- a fifth value (`partially_delivered`) is refused BY THE ENUM, which is what
  makes "a fifth outcome is a report" a refusal rather than a convention;
- an outcome row with NO outcome is refused by the CHECK;
- an ordinary row CARRYING an outcome is refused by the same CHECK, the other
  direction;
- all four ruled values accepted, and an ordinary attempt row accepted.

**Proven at the route**, five tests, the new one proven red first with the
mutation confirmed landed: removing the `denied` producer while leaving the 403
turns it red, restoring it green. The other four assert the typed column rather
than the jsonb string, and the attempt-row-first test is untouched and still
passes, so the audit invariant's ordering is asserted across every outcome.

**The change log now says WHICH outcome** rather than delivered-or-not, in four
readings a person can act on. That is the ruling's four values arriving where
they were always meant to be read.

## What a later reader should not misread

`detail.outcome` and `detail.delivered` are GONE from new rows: the column is
the one fact and two copies drift. Rows written before 0068 carry the old
strings AND get the column from the backfill, so the render reads the column for
every row and needs no fallback.
