# Session log: Q-12b-3, `fallback_plan` (shadow)

**Queue row:** Q-12b-3, next in order. **Spec:** RFC-ATTR-01 Amendment 1
section A1.3, which names the five-value vocabulary verbatim and says
"Absent; new migration required". **Migration:** one (0073).

## The founder's reading, which settles the hardest part before it is built

Given 5 September 2026, and it removes the only question this row would
otherwise have to stop on:

1. **The five steps are the vocabulary AS WRITTEN**: `preferred`,
   `approved_substitute`, `established_backup`, `vetted_bench`, `ask`. Not
   renamed, not extended, not reordered.
2. **Which step is permitted without asking is READ FROM DECISION RIGHTS**,
   never minted here, on the every-ceiling-permits reading.
3. **If a per-household ordering is needed, that is a DECISION to report**,
   not something to build.

## What the five steps mean, and why the order is not mine to choose

The vocabulary is a LADDER: `preferred` is what the household wants,
`approved_substitute` and `established_backup` are things somebody already
approved for this household, `vetted_bench` is a company-vetted option nobody
has approved for this household in particular, and `ask` is the floor. **The
ladder's ORDER is given by the vocabulary itself** (the RFC lists it in that
order and the words describe descending closeness to the household's own
choice), so no ordering is invented by building it.

**What IS a per-household question, and is reported rather than built:**
whether a given household's ladder skips a rung. Two households could
reasonably differ on whether `vetted_bench` is reachable without asking at
all. Nothing in this build lets a household reorder or skip, and nothing
assumes they cannot; the column records which step a plan reached, and the
authority question is answered per attempt by the rights.

## The authority rule, applied rather than restated

**A step is permitted without asking only if the household's Decision Rights
permit it, under the standing rule that a grant in one domain never governs
another.** So the permission question is asked per FALLBACK PLAN against the
right its own row names, exactly as `expected_event` does, and the composition
where several rights share a materiality is the one already ruled: every
applicable ceiling must permit.

`ask` is the floor and needs no right: it is the step that means the authority
ran out.

## Shadow, and what this build deliberately cannot do

Year-two, `shadow`, on the same terms as its two siblings: computes, logs,
visible in the corporate portal, surfaces to no member and alters no HOM
briefing. **Nothing executes**, here as in Q-6: reaching a step means the
household's rights PERMIT it, and no execution engine exists to act on that.

## What was built

`fallback_plan` (migration 0073), the five-step vocabulary verbatim in the
spec's own order, two corporate acts kept separate (`recordFallbackPlan`
writes the ladder, `evaluateFallbackPlan` reads which step it reaches), the
pure `walkFallbackLadder` in `@wellkept/schema` beside the router it composes,
a drill-in card, the erasure treatment, the full legal set, and a journey.

**The reading writes no person.** `reached_step`, `reached_at` and
`reached_why` are stamped and nobody is attributed, because which rung a
household's own grant reaches is a fact about the grant rather than about the
operator who looked. `recorded_by` already names the attributable act, which is
writing the ladder down. The integration suite asserts the absence against
`information_schema` rather than trusting it.

## The acceptance criterion, met in part, with the parts named

**Met:** the approved substitute is reached, within the household's own
authority, before anyone is asked; `ask` is the floor that means the authority
ran out.

**Not met, and neither is a shortcut:**

1. **"is USED" is execution, and nothing here executes.** A reached step says
   what the grant permits. The journey proves the negative directly: no work
   item and no decision record appears behind an evaluation.
2. **"the preferred option FAILS" is a fact this table does not hold.** An
   option being ON RECORD and an option being AVAILABLE TODAY are two different
   facts and only the first is stored. So the walk skips an ABSENT rung and has
   no notion of a present one that failed. Inventing an availability state
   would be minting a vocabulary the spec did not give, so it is reported.

## The finding: a loop that described itself wrongly

The first version of `walkFallbackLadder` called the router INSIDE the rung
loop. That READ as four permission checks and was not one: none of the router's
inputs (rights, materiality, amount) changes between rungs, so all four calls
returned the same answer and the walk always stopped at the first rung with an
option on record.

**It was correct and it misdescribed itself, which is the worse of the two.**
A wrong answer gets found; a right answer reached by a mechanism the reader
misunderstands gets built on. The next person to touch it would have believed
the rungs were separately authorised and would have reasoned from that.

Restructured to ask the authority question ONCE, with the misreading recorded
in the module rather than quietly removed.

**And the question it raised is the founder's, so it is reported:** there is a
real argument that taking an `approved_substitute` exercises an approval
somebody already gave for this household, while taking a `vetted_bench` option
is a new act, and the two should not clear the same bar. Building that would
mean deciding that an approval in one domain governs an action in another,
which is exactly the standing rule's bar, and it would mean minting a per-rung
permission here.

## The every-ceiling-permits composition, and why saying it is a no-op matters

The plan NAMES its right, the caller-names-the-right rule `expected_event`
already holds. `decision_right_household_key_unique` makes at most one row
match a named key per household, so "every applicable ceiling must permit"
ranges over a set of at most one **by construction**.

It is written as a fold anyway rather than as a `.find()`, and the reason is
in the module: if that unique index is ever relaxed, the rule holds instead of
silently taking whichever row came back first. Stating the no-op is the point,
so a later reader does not discover it and read it as dead code.

## Erasure: the sibling treatment would have failed, and only on real data

Blanking free text to a constant marker is what every sibling table does. Here
it COLLIDES. `fallback_plan_one_per_choice` is unique on
`(household_id, choice)`, so blanking every plan of one household to the same
marker makes two erased plans duplicate, and the erasure fails on its last
household with several plans, **having passed every test written with one**.

Proven in SQL both ways by constraint name BEFORE the comment claiming it was
written: the constant form raised
`duplicate key value violates unique constraint "fallback_plan_one_per_choice"`,
the per-row form did not.

**The W-6 precedent generalizes:** blank to a marker rather than to NULL so the
CHECK survives, and where the blanked column is part of a UNIQUE key, the
marker has to be per row.

Then the tool's own statement was EXTRACTED FROM THE FILE and run verbatim
against Postgres inside a rolled-back transaction, because a dry run prints a
plan it never executes (G-125). Two plans blanked, uniqueness survived, and an
absent option stayed NULL rather than becoming an erased-something on the way
out.

## Proofs

- **Eleven SQL refusals by name, five accepting shapes**, each case in its own
  transaction per the G-129 remedy, with the constraints and the enum printed
  from `pg_constraint` before any case ran. Zero rows left behind, read back.
- **The eleventh case exposed a defect in the ASSERTION, not the case.** An
  enum error does not quote the type name, so the matcher missed a real
  refusal and reported it as a wrong answer. The wrong-unit class inside the
  checker itself; the case was right the whole time.
- **Ten integration tests, every one reading real `decision_right` and
  `fallback_plan` rows.** Written that way because of the standing rule this
  row's predecessor produced: `routeByDecisionRights` had seven green unit
  tests for a week and not one read a row.
- **All four censuses proven RED FIRST by name** (erasure, legal, archive,
  staff disclosure), then green with the treatments.
- **`success-visibility` and `action-permissions` each proven to SEE the new
  actions** by mutation, with the mutation confirmed landed first, then
  restored green.
- **The journey found its own page-wide locator.** The expectations card one
  section up carries inputs with the SAME aria-labels, so a bare `getByLabel`
  resolved to two elements and Playwright refused. It failed loudly; the
  version that silently fills the other card's input is the one to fear.
