# Session log: Q-12b-1, `expected_event` and the six launch patterns (shadow)

**Queue row:** Q-12b-1, next unblocked item after Q-11j (founder-side).
**Spec:** intake `BENCHMARK_ADOPTION.md` section 2 (verified@Q-0b, frozen,
adopted) and `RFC-ATTR-01` Amendment 1 section A1.3. **Migration:** one.

## What the spec actually says, quoted rather than paraphrased

Section 2: "`expected_event` patterns with `reconciliation_status` (matched,
missing_expected, unexpected, changed, conflicting, stale, cannot_determine)
and candidate decisions. Six launch patterns: vendor visit without invoice or
report; registration without confirmation; cancellation confirmed then charged
again; return shipped without refund; promised estimate overdue; annual
school-cycle packet missing. The household is never made to check."

A1.3: "**Absent; new migration required.** Nothing in the tree holds an
expectation pattern or a reconciliation status."

## The plan

**Adopted verbatim, not invented:** both vocabularies. The seven statuses are
the spec's own words. The six patterns are the spec's own sentences; only their
KEYS are minted, and the migration header carries each key beside the sentence
it transcribes, so the pack_key lesson holds (the key is the identifier, the
sentence is the display text).

**Three findings that shape the build, each read from the tree rather than
assumed:**

1. **A sweep cannot create a `decision_record`.** `routed_by` is NOT NULL
   referencing `auth_user`, and a sweep has no user. Inventing one is exactly
   what G-66 refused. So the candidate decision in shadow is recorded ON the
   expected_event row, personless, in the `time_segment` posture: a derived row
   is a system row carrying no person.
2. **`decision_record.audience` is CHECK-constrained to hom / corporate /
   founder.** There is no member audience, so nothing here can reach a member
   even by accident. That is construction, not discipline.
3. **`candidate_decision_refs[]` is deliberately NOT built as an array.** A
   Postgres array of ids carries no foreign key, so it cannot hold the
   composite `(household_id, id)` tenancy guarantee every other reference in
   this tree uses. The refs arrive as a reverse join when a human routes a
   candidate into a real decision record at promotion, which is a better
   relational shape than the array the RFC names. Reported, not silently
   dropped.

**Routing by materiality, and what is derived rather than chosen.** The
household's `decision_right` rows already carry `materiality` from the signed
source, so "routed by materiality" resolves to: take the rights of the
expectation's materiality and route through the existing
`routeByDecisionRights`. Where the expectation's materiality is NULL, or no
right of that materiality exists, the answer is `propose`, which is the
existing module's own null-threshold default and the doctrine's safe
direction. **One composition call is mine and is reported under the standing
tiebreak:** where several rights share a materiality, a candidate auto-executes
only if EVERY one of them would permit it. That keeps `auto_execute`'s existing
meaning (at or below the household's ceiling) intact under each applicable
ceiling rather than inventing a new one.

**Shadow, and what shadow means here concretely:** computes, logs, visible in
the corporate portal, surfaces to no member and alters no HOM briefing. So the
sweep writes NOTHING into `attention_record` (which would reach the previsit
brief) and nothing into any member-reaching channel. **The shadow-enablement
mechanism still does not exist (Q-11s)**, so this ships computing for every
household with expectation rows, and rows exist only where a corporate operator
recorded one.

**The producer, per column, so nothing ships inert by accident:** a corporate
action on the household drill-in records an expectation; the sweep writes the
reconciliation columns; two columns ship with no producer and say so.

## Verified, and what each harness does not reach

- **Suite 11/11 uncached, typecheck 13/13.** That covers unit and
  integration tests. It does not run the journeys and it is not CI.
- **35 journeys green** against a local dev server (one skipped: the Part
  B rehearsal, which needs a build).
- **CI has not run on this head**, so nothing here is a claim about the
  gates or airplane jobs.

**Seven SQL refusals by name, three accepting shapes**, with the
constraints printed from `pg_constraint` and the enum cardinalities read
BEFORE any case ran:

| Case | Result |
|---|---|
| a status with no time | refused, `expected_event_reconciliation_is_whole` |
| a time with no status | refused, same constraint |
| `matched` with no event | refused, `expected_event_matched_carries_its_event` |
| half a candidate | refused, `expected_event_candidate_is_whole` |
| a negative amount | refused, `expected_event_amount_is_not_negative` |
| a seventh pattern | refused by the enum type |
| a match from ANOTHER household | refused, `expected_event_matched_event_same_household_fk` |
| an open expectation, amount zero | accepted |
| a whole `missing_expected` with a whole candidate | accepted |
| `matched` with an event in its own household | accepted |

**The first attempt at that proof was worthless and it is worth saying
why.** A setup INSERT failed on `event_outbox.occurred_at`, which aborted
the transaction, so all ten cases returned "current transaction is
aborted" and every REFUSE case would have read as a pass to anyone
grepping for ERROR. That is the preconditions rule catching its own
proof. The rerun gives each case its own transaction and reads the
constraint NAME out of the message rather than the presence of an error.

**Four integration tests on the real database**, against the row's
acceptance criterion: a passed window with no match opens
`missing_expected` with a whole candidate; an unclassified expectation
PROPOSES; a `money_legal` expectation under the household's ceiling
AUTO-EXECUTES, routed by a materiality the row never named; a row inside
its window is untouched; the sweep is idempotent; and
`attention_record` and `decision_record` are asserted EMPTY, because
shadow is a claim about what was written.

**The journey caught its own defect on the first run**: `getByText`
matched both the select's blank option and the row's provenance line, so
the assertion was about the form rather than about the row. Located on
the row's own line instead.

## Reported, not asked

- **The composition call** where several rights share a materiality
  (every applicable ceiling must permit), under the standing tiebreak.
- **An allowlist addition**: `expected_event` joins the staff-disclosure
  allowlist for `recorded_by`, write provenance only. It is the FOURTH
  staff-attributed table to ship since G-13 became a hiring precondition,
  and it is named as an allowlist addition rather than buried, since
  widening one is never pre-authorized.
- **`candidate_decision_refs[]` is not built**, and the reason is the
  tenancy guarantee rather than scope.

## Open items

- **`matched` has no producer** and no other status but `missing_expected`
  is written today. Matching a signal to an expectation is Q-12b-2's
  changeset work; the column and its FK ship so it lands without a
  migration.
- **Shadow enablement does not exist (Q-11s)**, so "on for the test
  households the day it ships" cannot be honoured by a switch. It
  computes wherever an operator records an expectation.
- **Owed at the next deploy: 0069 applies (69 to 70).** Additive,
  server-only, no member-facing change.
