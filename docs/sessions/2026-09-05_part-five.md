## Part Five item 1: the operational health surface, BUILT

`/oversight/health`, corporate-gated, four signals in one place:
worker drain lag, dead-lettered outbox rows, mail webhook silence, and
migration drift.

**Three of the four existed SCATTERED and the fourth did not exist at
all**, which is not two separate facts. A drain line lived on the fleet
board, a mail card beside it, and migration drift nowhere: a signal with
no home is a signal nobody notices is missing.

**The alerting posture is rendered, and it is that there is none.**
Nothing pages, emails, or writes to the firewall; this is a page a
person opens. Stated on the page and again in the module, because a
health surface that looks like monitoring and is not converts "we are
not watching" into "we watched and it was fine".

**Thresholds are not invented.** Two signals have a correct value of
ZERO by definition and state a verdict without one (migration drift,
dead-lettered rows). The other two report the reading and say THRESHOLD
UNSET, which is the visit_reconciliation posture.

**The migration count is baked in at BUILD time** (`migration-manifest.ts`,
importing the journal) rather than read from the filesystem, and the
distinction is the point: the question is whether the database agrees
with THE CODE THAT IS RUNNING. A filesystem read answers a different
question wearing the same words. This is the signal G-120 needed and did
not have, from the other side.

**Proven both directions on a real database**, on the one signal whose
verdict does not wait on a founder threshold: green when the counts
agree, and red when a row is deleted from `drizzle.__drizzle_migrations`,
with the mutation confirmed landed before the result is read and the
message asserting it names the UNSAFE direction.

**The proof's own restore was wrong first and is worth recording.** It
re-inserted a row hashed `operational-health-proof-restore`, which put
the COUNT back and left the migrations table asserting that a migration
nobody wrote had been applied. It passed its own assertion because the
assertion only counted. Now the row is captured before the delete and
written back verbatim, and the restore asserts the HASH rather than the
count. The local database was repaired the same way, with 0066's true
sha256.

**Two schema tests** assert the journal and the `.sql` files on disk
agree, which `deploy.sh` checks before every deploy and nothing checked
in CI. A drifted journal would make the health surface report a
confident wrong number.

## Part Five item 2: the restore drill, repo-side half BUILT

`pnpm db:restore-drill`, two modes, **both strictly read-only**, which is
deliberate rather than incidental: the verify mode runs against the
restored database, the one place a stray write would corrupt the thing
being verified.

**Row counts are the wrong assertion for a point-in-time restore** and
the design says so: production keeps moving, so equal counts fail for a
healthy restore taken a minute earlier. Counts are compared with a
never-emptied rule, and the real assertion is a CONTENT HASH over the
oldest `audit_event` rows, which are append-only by law and cannot
legitimately differ.

**Proven both directions on real databases.** Green: baseline and verify
against the seeded local database, five checks pass. Red: a fresh
database migrated to the same count, verified against the same baseline,
and **migration count and table presence PASS while the two content
checks FAIL by name**, listing thirty tables that had rows and came back
empty. That is exactly the empty-schema restore, and the fact that two
checks pass in that scenario is why the other three exist. Three
refusals proven too.

**The proof caught a real defect on its first run:** the first version
used `--baseline` as both the mode flag and the file argument, so the
documented `--verify --baseline <file>` set both modes and the script
refused its own instructions. Fixed to `--from`.

`docs/RESTORE_DRILL.md` carries the exact Neon steps and the expected
output of each, including the vault decrypt as step 4, which is
deliberately manual: automating it would mean handing `WK_KMS_KEY` to a
drill tool to decrypt a real secured value.

## TWO BUILD BREAKS I CAUSED AND FIXED, both reported rather than quietly repaired

**1. The `@opentelemetry/core` override broke the build, and the
advisory cannot be closed that way.** 2.x removed `getEnv`, which
`@opentelemetry/resources@1.30.1` and `sdk-trace-base@1.30.1` still
import, both arriving through `@sentry/node@9.46.0`. Reverted. **So the
honest count is eight advisories, not seven**, and the audit document is
corrected. The lesson, made inside a session about being careful: a
transitive override across a MAJOR version is a change to code nobody
here wrote, and only a build can say whether its dependents survive it.
I bumped it and reported it closed in the same breath.

**2. Exporting the restore drill from the schema index dragged `pg` into
the CLIENT bundle**, through trigger-engine to VisitWizard, failing with
"Can't resolve 'fs'". The household export and import scripts already
follow the rule I broke: a CLI module is wired as a script and never
re-exported from the barrel. Fixed and the reason written into the
module.

Both were caught by `pnpm test --force` running the web build, which is
the argument for running the full suite rather than the package's own
tests.
