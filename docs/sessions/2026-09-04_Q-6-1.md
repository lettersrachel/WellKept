# Session · 4 September 2026 · Q-6-1, the Decision Rights block

Q-6 split into Q-6-1 and Q-6-2 by founder ruling, one migration each.
This is the first: the routing TABLE, which has to exist before Q-6-2
can route on it.

## Plan, written before code

### The object

`decision_right`: one row per household per right. The Decision Rights
block of the Four-Stage spec's section 1, which Q-6-2 reads as its
routing table.

**Value shape: two columns, whole or absent.** The 17 seed rows carry
two kinds of value and one column cannot hold both honestly. Spend
ceilings are money and the standing rule is integer cents;
`vendor_substitution` is `approved_substitute_only`, which is a word.
So `value_cents` and `value_text`, with a CHECK that EXACTLY ONE is
present. A single text column would store `"15000"` beside
`"approved_substitute_only"` and lose the money rule.

**Zero is a MEANINGFUL value here, unlike 0052.** A ceiling of zero says
spend nothing without asking, which is a real instruction a household
might give. So zero is accepted and only NEGATIVE is refused. Recorded
because the neighbouring precedent points the other way and a later
reader would otherwise assume it applies: in `estimate_snapshot` zero
was the ambiguous unknown and NULL was honest; here the absent ROW is
the unknown, and zero is a decision.

**Confirmation is whole or absent, both directions**, the house CHECK:
a confirmed row carries `confirmed_at` and `confirmed_by` together, a
recommended row carries neither. `confirmed_by` records WHO SAID
SOMETHING, so per the rule added with 0065 it is nullable with no
default; `status` is NOT NULL with no default either, so nothing
silently becomes recommended without the loader saying so.

**The tier is NOT stored on the row.** The household carries its tier;
the loader reads it to pick a column. Storing it again would mean a
tier change silently rewrites rights the household may since have
confirmed, which is the wrong direction: these are the household's
rights now, and a tier change is a conversation, not a migration.

### The loader (`pnpm db:decision-rights`)

Reads the FROZEN CSV at
`docs/intake/2026-09-04-founder-values/decision_rights_by_tier.csv`
rather than restating its figures in source, per the founder's ruling:
the figures entered once under the intake that hash-pinned them, and no
second copy exists to drift from the first.

Three mappings the loader must make, each named rather than silent:

1. **`family_operations` (CSV) to `family_ops` (shipped enum).** The
   shipped tier vocabulary is `essential | family_ops | concierge` and
   the CSV column header is `family_operations`. Adoption MAPS, never
   renames (the status-tag ruling, now the second instance in this same
   package). Neither side is edited.
2. **USD to integer cents.** The CSV says `150`; the column stores
   `15000`. The standing money rule is the reason, and the conversion
   is proven by name rather than assumed.
3. **The two materiality residues, already on the record** (values-intake
   ground truth 9). `decisions_that_always_require_member` carries
   materiality `all` and `authority_review_cadence` carries a blank, and
   **the signed three-value enum can store neither**. The enum is NOT
   widened. Those two rows land with materiality NULL, each named in the
   loader with its written reason, and the loader PRINTS which rows it
   left null and why, so the gap is visible rather than lost. `all` is
   not a fourth materiality; it is a statement that the right applies
   across all of them, which is a different question and is Q-6-2's or
   the founder's, not a value to invent here.

**Provenance visible rather than implicit**, per the ruling: every
seeded row lands `status = 'recommended'` with an `authority` string
naming the frozen file and its row, and the corporate drill-in renders
a RECOMMENDED, NOT YET CONFIRMED tag on every unconfirmed right. A
person reading the block sees which rows are the company's guess and
which the household actually agreed to.

### Freeze posture

The member-facing surface does NOT ship and is not built and hidden
behind a flag. No client projection exists, so any recognizable
`decision_right` row in a client payload is a violation, and
`assertNoAnticipationRows` gains that signature (the `paused_decision`
posture). The corporate view is the only reader.

### Deliberately NOT in this session

- Routing. Q-6-2 reads this table; nothing routes yet, and the stage
  column stays unwired.
- The confirmation ACTION. Rows land recommended and the confirming
  surface is a corporate act that belongs with the ledger, since
  confirming a right without a ledger to route into changes nothing.
  Stated so the absence reads as a decision.
- Any global threshold knob. The authorization is explicit that none
  survives this item: thresholds are per-household Decision Rights.

## Verified

TYPEs, the table with its three CHECKs inline, the two foreign keys,
then the indexes. Both FKs reference PRIMARY KEYs on tables that already
exist, so unlike 0058 and 0063 there was no composite-key-before-index
hazard and no reorder was needed. Purely additive.

**And the first attempt at proof 1 found something worth reporting.**
Removing ONLY the executable `UPDATE decision_right ...` left
`erasure-coverage` GREEN, because the guard matches the table NAME
anywhere in the tool and the header comment still named it. So the guard
proves a table was CONSIDERED, not that anything happens to it: a
treatment described in the header and never written would pass. That is
adjacent to its stated not-covered column ("whether the treatment is
correct") but weaker than that column implies, since it does not check
that a treatment EXISTS in code. Reported, not fixed: it is a change to
a shipped guard, outside this item, and narrowing it to executable
statements is a session with its own both-directions proof.

**CORRECTION to that report, same day, by the session that made it.**
The behaviour is real and the founder's ruling to queue it stands, but
**it is DELIBERATE AND DOCUMENTED rather than an unnoticed hole**, and
the difference changes the queue item from fixing a defect into
revisiting a decision. The guard's own header says so in as many words:
"a comment naming the table counts exactly as much as a query does (the
floor is being NAMED, the treatment decision, not a particular SQL
shape)", and it even records the proof shape this session used,
"blanking every standalone mention of one table turns the suite red".
So the floor was chosen to force an author to DECIDE, and it does that.
What I reported as a gap is the floor working as designed.

**The finding that survives** is narrower and is still worth the queue
row: a treatment described in a comment and never written would pass,
and whether that floor is still the right one is the founder's call.
Q-6g is corrected to say so, including what to do if the answer is that
the floor stays.

**Why I did not catch it in the moment**: I read the guard's ASSERTION
to understand what it computes and did not read its header, which is
where the design decision lives. The header was two screens above the
line I was reading. That is the same shape as reading a citation as
evidence rather than as an instruction to go and check, applied to a
comment block instead of a document.
