## Plan (written before building, per the merged queue discipline)

**Read first (done, via six parallel readers over the tree):** the mail
package and all five send paths; all 61 exported server actions across
the two "use server" files and every gate shape; the app_setting knob

**1. Migration 0062 `mail_outcome`** (idx 62), the session's one
migration. Columns: id, provider_event_id (unique, the svix delivery
id, the dedupe key), kind (the provider's own event type verbatim, no
invented vocabulary and deliberately no CHECK: a vendor's event list
grows, and an evidence table stores what arrived), recipient, message_id,
household_id (nullable FK, resolved at write time from the recipient's
client assignment; null for staff mail, sign-in links, and ambiguous
addresses), payload (the verbatim event body), occurred_at (provider
clock, nullable), received_at. Producer per column: every column is
written by the webhook route, one producer for the whole table.

**2. The webhook route** `POST /api/webhooks/resend`: raw-body read,
Svix-scheme HMAC-SHA256 verification with node:crypto and
timingSafeEqual (no new dependency; the repo has no HMAC helper, so the
route carries its own, following the totp package's timing-safe
precedent), five-minute timestamp tolerance, fail closed three ways
(503 when RESEND_WEBHOOK_SECRET is unset, 401 on a bad signature, 400
on a stale timestamp or malformed body). Dedupe by
onConflictDoNothing on provider_event_id. Every accepted event also
plain-upserts app_setting `mail_webhook_status`
({lastReceivedAt, lastKind}), the outbox_drain_status precedent: a
heartbeat is state, not a decision. No rate limit: the limiter fails
open by design and the signature is the credential.

**3. Corporate visibility**: a "Mail deliverability" card on the fleet
board (the Company time card precedent): bounce and complaint counts
for the trailing 30 days, each recent bounce/complaint with its
household name where linked, the last-webhook heartbeat line, and a
silence alert driven by a founder-set knob `mail_webhook_silence`
({maxQuietDays: null}) that surfaces NOTHING while null, the
visit_reconciliation pattern exactly. No setter ships; the knob is
founder-set. The acceptance's "within one worker cycle" is met by
construction: the board reads the table directly, no worker involved.

**4. The action-permission guard** `apps/web/src/lib/action-permissions.test.ts`:
the queue row's lint-level declaration in the repo's own guard idiom.
The census computes both its inputs: every "use server" file (first
line is the directive, which excludes totp.ts's comment mention), every
exported async function in each (the success-visibility enumeration and
brace-matching shapes), and asserts each body calls a recognized
permission gate (getPrincipal, getStaffIdentity, guardedUser,
getSessionUser) or carries a written allowlist reason. One allowlist
entry at birth: dismissRecoveryCodesAction (clears a display cookie
only, no read or write beyond the viewer's own cookie jar). Floors:
at least 2 files, at least 55 actions. Reverse direction: a stale
allowlist entry (action gone, or action now gated) fails. Proven red
two ways (allowlist entry removed; a planted gate-less action) and
green restored. Joins guards-manifest (files array and the CLAUDE.md

## Ground truth

1. The row's spec (Architecture Review §4) is not in the repository;
   the row ran on its acceptance criteria alone, as the re-cut queue
   already recorded.
2. The acceptance's `defineAction` wrapper is NOT built; the
   action-permission guard is the lint-level enforcement of the same
   rule, which the re-cut row explicitly permitted. Recorded as the
   settled shape. The guard's floor is the gate CALL; whether the role
   check beside it is right stays review (the not-covered column).
3. The census found exactly one gate-less action in the whole layer:
   `dismissRecoveryCodesAction` (mfa), which clears a display cookie
   and touches nothing else. Allowlisted with the reason rather than
   changed; giving it a gate would be scope.
4. The acceptance's "corporate sees it within one worker cycle" is met
   by construction (the board reads the table; no worker exists in the
   path), stated so the wording is not over-read as a worker feature.
5. Silence-knob semantics carry an ambiguity the founder should know
   when setting it: if only bounce and complaint events are subscribed,
   a quiet webhook is ALSO the healthy state. Subscribing
   email.delivered makes silence mean liveness. The knob ships quiet
   and the choice is hers.
6. RESEND_WEBHOOK_SECRET is deliberately NOT added to deploy.sh's
   required-env gate: the route fails closed without it and a deploy
   must not be blocked on webhook configuration.
