# Session · 4 September 2026 · Q-5, the pipeline stage enum

Queue item Q-5, authorized by the founder at the Q-1 activation. Spec:
the Four-Stage Application Spec, stamped plan-of-record in
`docs/SPEC_REGISTER.md:41` and present as
`docs/library/WK_Four_Stage_Application_Spec_2026-08-02.docx`. The
authorization carried two acknowledgements, both of which shape the
plan rather than decorate it:

1. `trigger_rule.stage` **ships inert**, and the migration header says
   so **alongside the producer table** (the per-column producer rule,
   G-85).
2. The forbidden-key assertion for `stage` **covers any client payload
   rather than relying on absence**.

## Plan, written before code

### What the spec asks for, and which half is buildable today

The spec's section 3 asks for three things. They are not equally
reachable from this tree, and the difference is the plan:

- **The stage tag.** "Every trigger, prompt-pack item, requirement, and
  queue item carries its stage as an enum: anticipate, identify,
  decide, monitor." Buildable now. This is Q-5.
- **The pipeline as state machine**, whose routing table is the
  Decision Rights block: "below-threshold items auto-execute and log in
  full, propose-first items enter the decision inbox, never-decide
  items block until the household speaks."
- **The decision inbox**, a member surface.

**The routing half of Q-5's own acceptance criterion is not
satisfiable in this session**, and the reason is a missing
prerequisite rather than a shortfall of effort. "Below-threshold" and
"above-threshold" are read against the Decision Rights block, which the
spec's section 1 places in the Playbook and which the re-cut queue
places in **Q-6**. No thresholds table, column or knob exists in this
tree. Choosing one here would be choosing a threshold, which standing
law forbids in as many words, and it would look like a decision
somebody made. So this session builds the tag and reports the routing
half against its prerequisite, per the queue's report-and-stop rule.

The decision inbox is a member surface and is FREEZE-GATED under Part C
§2.2 regardless.

### The migration (0065, this session's one)

`CREATE TYPE pipeline_stage AS ENUM ('anticipate','identify','decide','monitor')`,
the spec's four values verbatim and in its order, plus one column on
each of the three carriers the queue row names.

**Producer table, per column, in the migration header** (G-85: per
column, never per migration):

| Column | Producer |
|---|---|
| `trigger_rule.stage` | **NO PRODUCER YET.** A rule's stage is a corporate-authored classification of what the rule is FOR; nothing computes it and no surface writes it. Nullable, no default, so no row carries a stage until a person sets one. The authoring surface is a later session. |
| `prompt_pack_item.stage` | **`packages/trigger-engine/src/run.ts`**, both insert sites (`runTriggerPass` and `runRegistrySweep`), which stamp `anticipate` explicitly. This is the acceptance criterion's first clause: a fired trigger lands in `anticipate`. |
| `work_item.stage` | **NO PRODUCER YET.** A work item arrives from `hm_capture`, `corporate` or `system`, and none of those three determines a stage without a taxonomy nobody has ruled. Nullable, no default. |

Two of three columns are therefore deliberately inert, which is the
state G-85 exists to make visible rather than to prevent: schema ahead
of its writer is fine deliberately and not by accident, and after the
fact the two look identical. The header is what tells them apart.

**The one default, and why it is not an invented classification.**
`prompt_pack_item.stage` is `NOT NULL DEFAULT 'anticipate'`. The
default exists for the backfill of existing rows, and its value is the
spec's own answer rather than mine: every row in that table is a fired
trigger's artifact, and the spec says a fired trigger is in
`anticipate`. The engine still writes the value explicitly at both
sites, so the producer is real code that a test can prove, not the
database's default standing in for one.

**`decision_record` is deliberately NOT tagged.** It is not among the
three carriers the queue row names, and a `decide`-stage column on the
table whose every row IS a decision would be a stored constant.

### The vocabulary module

`packages/schema/src/pipeline-stage.ts`: the four values as the single
exported list, with an exact-list pin in the guard so the enum and the
module cannot drift (the `field-attributes.ts` shape from Q-4/B1).

**Deliberately NOT built: a transition table.** The spec's flow
sentence names FIVE movements ("anticipation, identification,
decision-routing, execution, monitoring") against a FOUR-value tag,
with `execution` absent from the enum. That gap is reported below, not
closed here, and a legal-transition helper with no consumer would be a
mechanism built because analytics might someday use it, which the
standing collection-side rule bars.

### The guard (acknowledgement 2)

Guardrail §5 of the spec: "Stage tags are internal; no member surface
ever displays the schema."

Two client-payload mechanisms exist and each covers a different family,
so `stage` is refused by BOTH rather than by whichever one a future
payload happens to call:

1. **`assertNoAnticipationRows`** (`packages/schema/src/standards.ts`),
   the recursive signature guard already wired into every client
   payload boundary. Every clause it holds today is a KEY PAIR, which
   is exactly the reliance the acknowledgement rules out: a pair
   depends on the companion key being present. The stage clause is a
   **single key** whose value is one of the four, refused at any depth,
   in an array or nested object, with no companion required. Happy
   accident worth stating: `stage` has no snake_case variant, so the
   camel/snake double-check every other clause carries collapses to one
   form here.
2. **`assertDeclaredClientKeys`** (`packages/permissions/src/index.ts`),
   which governs the declared-list payloads (playbook fields, registry
   entries, the client visit report). A new `FORBIDDEN_CLIENT_KEYS`
   set makes `stage` throw **even when it is declared**, so the
   declared-list hatch cannot be used to publish one. Without this,
   the client report projection would be governed only by a list a
   future author could widen.

Proof obligations, both directions, per standing doctrine: red on a
planted `stage` at top level, nested, and inside an array; red on
`stage` added to a declared list; green on the real client payloads
unchanged; and green on a key named `stage` holding a value outside
the vocabulary, which is the stated residue.

### What is NOT owed, with the reasoning stated rather than skipped

- **Erasure treatment.** No new table. All three carriers already have
  written treatments in `erase-household.mjs`'s header
  (`trigger_rule` kept-and-disabled, `prompt_pack_item` text blanked,
  `work_item` words blanked and skeleton kept). A `stage` column holds
  no free text and no fact about the household, so no treatment
  changes and the eleventh deletion exception is not in play.
- **The same-PR legal rule.** `stage` is not a new data category: it
  records our own pipeline classification of our own record, not
  anything collected from or about a member. legal/README, both
  privacy copies and CHILD_DATA are unchanged, and the two computed
  censuses (erasure-coverage, legal-census) are table-scoped, so
  neither input set moves.
- **The staff-disclosure guard.** The column names no person.
- **`judgment-free` and `field-attributes`.** `stage` matches no
  judgment-free pattern and carries none of the four attribute shape
  words.

Each of those is asserted by running the suite, not by this paragraph.

## Reported, not resolved

1. **The routing half of the acceptance criterion is blocked on Q-6.**
   Named above. Nothing here routes on a threshold, because no
   threshold exists to route on.
2. **Four enum values against a five-movement flow.** The spec's
   section 3 sentence names `execution` as an explicit state; the
   stage tag it specifies two paragraphs later has four values and no
   `execution`. Both are the spec's own text. Reported per the
   standing rule that a document disagreeing with itself is reported
   rather than reconciled; the four-value list is built because the
   queue row and the spec's tag sentence both name exactly those four.
3. **The roadmap test the tag exists to mechanize is a review
   process, not code.** "Anything tagged `decide` receives the
   returned-choice design review before it ships" governs FEATURES,
   which live in the requirements document and the build queue, not in
   these three tables. The schema column and the roadmap test share a
   vocabulary and not a mechanism, and reading the column as the
   roadmap test would be the G-109 shape (two measurements sharing one
   name).

## Verified

**Migration read before applied**, per the standing rule. drizzle-kit
emitted `CREATE TYPE` first and the three `ALTER TABLE`s after, which is
the order Postgres requires, so unlike 0058 and 0063 no reorder was
needed. Purely additive: one CREATE TYPE, three ADD COLUMN, no DROP, no
ALTER COLUMN, no RENAME, nothing made NOT NULL on existing data without
a default.

**Applied locally and read back BY QUERY, not from the screen:**

- `enum_range(null::pipeline_stage)` returns the four values in the
  spec's order.
- `information_schema.columns`: `prompt_pack_item.stage` NOT NULL
  defaulting `'anticipate'::pipeline_stage`; `trigger_rule.stage` and
  `work_item.stage` both nullable with NO default, which is what makes
  "ships inert" structural rather than a promise.
- The backfill: all 9 existing `prompt_pack_item` rows read
  `anticipate`, and nothing else exists to be classified.
- `registry_entry` has NO stage column, asserted because the client
  registry payload is a SPREAD of every column, so a stage column on
  that one table would reach a member the moment it existed.

**Four red proofs, each with the mutation CONFIRMED LANDED before the
result was read** (a mutation that never applied and an assertion that
cannot fail produce the same green run), and each anchor asserted unique
so an ambiguous replacement refuses rather than half-applying:

| Mutation | Confirmed landed by | Result |
|---|---|---|
| the single-key stage clause removed from `assertNoAnticipationRows` | the clause absent (0 matches), the marker present (1) | RED, 1 failed of 11 |
| `stage` removed from `FORBIDDEN_CLIENT_KEYS` | the entry absent (0), the marker present (1) | RED, 2 failed of 26 |
| `execution` added to the `pipeline_stage` pgEnum | the drifted list present (1) | RED, the drift case only |
| the engine's explicit `stage: "anticipate"` removed | the marker present (1) | RED, and on the right message: "the insert omitted stage; the column default would supply it and the producer claim would be false" |

All four restored and re-read green.

**The producer proof is a captured-VALUES test, deliberately, and that
is the whole point of it.** The column carries `DEFAULT 'anticipate'`,
so a row read back from Postgres says `anticipate` whether the engine
wrote it or the database did. Those are two different claims and only
one of them is the per-column producer requirement. Reading the insert's
own values object is what tells them apart, and red proof 4 is the
direction that goes red when the explicit write is removed while a
database read would have stayed green. Recorded because the same shape
will recur on the next column that ships with a default.

**Suite:** `pnpm test --force`, 11 turbo tasks, 0 cached, all
successful. `pnpm -r typecheck` green in every package, including
`packages/schema` and `packages/trigger-engine`, which is the PR #203
lesson (vitest does not typecheck, and the package the new file is in is
the one that gets skipped).

**The obligations checked rather than assumed:** the two computed

no table, so neither input set moved; all three carriers already have
written erasure treatments and a `stage` column adds no free text and no
household fact, so none changes; `stage` matches no judgment-free
pattern and carries none of the four attribute shape words; the column
names no person, so the staff-disclosure census is unmoved. Each of
