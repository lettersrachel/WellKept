# K-OPS-002 re-point trace, and what of it can be run from here

28 August 2026. K-OPS-002 is being re-pointed from Jobber to the monorepo per
D1. This document holds the trace, the four rows already ruled, and the reason
the rest of it is not filled in.

## 1. The blocker, stated first because it decides how to read the rest

**K-OPS-002 is not in this repository, and neither is anything that names its
rows.** Verified by search across the whole tree: zero matches for
`K-OPS-002`, for `09_Operations`, for `OPS_ORG`, for ruling `A228`, and for
`PAPER-PARITY`. The document lives in the library and the library is not
mirrored here beyond the files listed in `LIBRARY_INDEX.md`.

So the fourteen original rows and the seven v1.1 parity additions **cannot be
traced**, because tracing a row means reading what the row claims and then
reading the code to see whether it holds. I have the second half and not the
first.

**What I will not do, and why it is worth saying rather than just not doing
it.** A row list could be reconstructed from what an operations SOP for this
company would plausibly contain, and the reconstruction would look like a
trace. It would be a document that reads as twenty-one verified rows and is
actually a guess with code citations attached, which is a worse artifact than
an empty one. The instruction for this trace was explicit about not inferring
from the SOP, from the row's own expectation, or from the interim control.
Inferring the row itself is the same error one level up.

**What would unblock it, exactly:** the row list. Subject and expectation per
row is enough; the full SOP text is not needed. Twenty-one lines pasted into a
session, and the trace runs against code the same day.

## 3. The seventeen rows this document is a placeholder for

Deliberately empty. The table below is the shape the trace will take, so that
when the row list arrives the work is filling cells rather than deciding a
format.

| # | Row (subject) | Expectation as written | Verified | How the behaviour actually works | Evidence |
|---|---|---|---|---|---|
| | *awaiting the row list* | | | | |

**The rules that will govern filling it**, recorded now while nothing is
pending, because the convenient reading is easiest to adopt once a row is in
front of you:

- **Verified reads against the code, never against the SOP, the row's own
  expectation, or what the interim control assumes.** All three describe
  intent. Only the code describes behaviour.
- **Partial means the mechanism exists and something material about it does
  not hold**, and the note says which. Partial with no note is a yes wearing a
  hedge.
- **Every cell in the evidence column is a file and a symbol.** "The code does
  this" without a citation is the class of claim this repository does not
  accept from itself.
- **A row whose subject cannot be located in the code is `no`, not
  `unverifiable`.** Unverifiable is for a row whose SUBJECT is outside the
  repository (a paper process, a founder-side account, a vendor behaviour).
  The distinction matters because `no` is a finding and `unverifiable` is a
  boundary, and collapsing them makes the trace look either worse or better
  than it is depending on which way the collapse runs.

## 4. The PAPER-PARITY acceptance test

Also not traceable from here, and worth naming separately from the rows
because it is a different kind of object. An acceptance test states a
condition the whole document has to meet, so it cannot be assessed row by row
and cannot be assessed at all without its text.

What can be said: **three of the four ruled rows resolve to paper.** The ACH
mandate is paper, the s3 values are paper, the training gate is a manual CEO
gate. If PAPER-PARITY asks whether the software matches what the paper process
does today, those three are parity by definition, since the paper process IS
the control. If it asks whether the software could replace the paper, they are
all three no. **Those are opposite answers to the same test**, and which one
the test is asking is the first thing to read when its text arrives.

## 6. The schema RFC question, report only

**Two RFCs are named and they are not the same document.** Stated plainly
because the consequence of assuming they are is a September deliverable that
turns out to be two, and September starts in four days.

**What the handoff's Gate 2 asks for** (line 266, item 2 of two): a
*coordinated field-attribute extension*, defining "provenance/knowing state,
source-vs-derived, derivation expression, confidence, materiality, consequence
class, lifecycle/staleness, and judgment-free schema constraints **once** in a
schema RFC. Migrate incrementally after repo reconciliation." Its purpose is
named in the risk table at line 1194, R9, schema fragmentation:
"Anticipation/verification/features could add overlapping columns/events. One
schema RFC and transactional outbox before feature expansion."

**What exists in the repository:** exactly one RFC,
`docs/rfc/RFC-PRIM-01_Domain_Primitives.md`. It is a **domain primitives** RFC
written to handoff section 5, classifying nine primitives EXISTS / PARTIAL /
ABSENT against the schema and ordering the migrations that followed. It is not
the field-attribute RFC and does not claim to be. **Gate 2's item 2 does not
exist.**

**Whether K-OPS-002's "September schema RFC" is the same document as Gate 2's
cannot be answered from here**, for the same reason the trace cannot be run:
the text naming it is in the library. What CAN be said, and it is the useful
half:

- **There is room for exactly one field-attribute RFC and it is unwritten.**
  If K-OPS-002's September RFC is about field attributes, it is Gate 2's item
  2 and they are one document. Two would be a duplication with no subject to
  divide between them.
- **The subject matter is not hypothetical, which is the argument for writing
  it once and soon.** The attributes Gate 2 lists are already implemented
  ad hoc in several places, each having invented its own shape: provenance is
  stamped server-side on every write; `preference_rule` carries a three-class
  provenance vocabulary plus a confidence column whose SCALE was deliberately
  left uninvented; `time_segment` carries `derived_from` and a source
  vocabulary distinguishing derived rows from refinements; `estimate_snapshot`
  treats NULL as the honest unknown and refuses zero. Those are five
  independent answers to "how does this column say where it came from and how
  much we trust it". **That is R9 happening, not R9 being prevented**, and it
  is the strongest case for the RFC being one document written before the next
  primitive lands.
- **What would settle the question in one line:** whether K-OPS-002 v1.1's
  reconciliation-event sentence names field attributes, or names something
  else (a Jobber-to-monorepo field mapping, for instance, which would be a
  genuinely different document).

No RFC is written here, per the instruction.
