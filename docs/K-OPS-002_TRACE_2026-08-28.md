# WK-OPS-002 platform capability trace, run against the monorepo

28 August 2026. The document is being re-pointed from Jobber to the monorepo
per D1. Rows supplied by the founder verbatim from the library archive; this
is the trace run against the code.

**Method, and it is the whole value of the exercise.** Verified is read from
the code and nothing else. Not from the SOP, not from the row's own
expectation, not from what the interim control assumes. All three describe
intent; only the code describes behaviour. Every verdict below carries a file
and a symbol, and where a one-line expectation is not enough to trace
against, the row says so rather than guessing what the SOP meant.

**Vocabulary, fixed before the first verdict so it cannot drift row to row:**

- **yes**, the behaviour exists and holds.
- **partial**, the mechanism exists and something material about it does not
  hold, and the note says which. Partial without a named gap is a yes wearing
  a hedge.
- **no**, the subject is absent from the code.
- **unverifiable** is reserved for a row whose SUBJECT lies outside the
  repository (a paper process, a device behaviour, a vendor). It is not a
  softer `no`. Collapsing the two makes the trace read better or worse than
  it is depending on which way the collapse runs.

## The ten rows verified

### Row 3. Per-user access logs: who viewed or used which household's access data, and when

**Verified: partial.** Two different halves, and only one is software.

**Viewed is logged, and logged well.** `api/reveal/route.ts:59-70` writes an
`audit_event` carrying `householdId`, `actorUser`, `actorRole`, `fieldId`,
`kind` (`s3_reveal` or `s3_corporate_view`) and `detail: { field, at }`,
**before** the value is decrypted, and a failed audit write refuses the reveal
(`route.ts:68-70`). Who, which household, which field, when, and under which
role. That is the row's question answered directly.

**The gap is one the code already documents against itself (G-53).** The row
records that a reveal was AUTHORIZED and ATTEMPTED, not that a secret reached
anyone. On 2026-07-29 three identical rows covered one real exposure and two
failures. So the log answers "who was permitted to see this and asked for it",
which is not quite "who viewed it".

**"Or used" has no representation at all.** Key sign-out, physical custody, a
code actually being entered at a door: none of that is in the system, and the
row's own interim control puts it on paper ("key sign-out records satisfy the
chain of custody"). Correctly scoped as paper, and named here so the trace
does not read as if the software covers it.

### Row 4. Photo capture inside the app that bypasses the device camera roll

**Verified: partial, and the two surfaces differ, which the row does not
anticipate.**

- **Native**: `ImagePicker.launchCameraAsync` after an explicit camera
  permission request (`hm-mobile/App.tsx:314-316`). That opens the camera
  directly rather than the photo library, which is the behaviour the row is
  asking for.
- **Web**: `<input type="file" accept="image/*" capture="environment">`
  (`VisitWizard.tsx:416-417`). `capture` is a HINT to the browser. On iOS
  Safari the picker can still offer the library, and the row's claim cannot be
  made for this surface from the source.

**Whether the captured image lands in the camera roll is an OS decision in
both cases**, and nothing in this repository asserts or controls it. Adjacent
and real: `jpeg-strip.ts` removes metadata before upload, which is a different
protection than the one this row asks for.

**The row's expectation is not traceable to a verdict from source alone.** It
says "verify capture path on iOS and Android", which is a device test, not a
code read. Named as a device test rather than an SOP ambiguity, because those
are different kinds of insufficiency and the remedy differs: this one needs a
phone, not a document.

### Row 5. One-tap client approvals for add-on quotes and over-limit purchases, logged

**Verified: no.** No quote object, no approval flow, no spending-limit concept
anywhere in the schema.

**What exists and is NOT this, named because it is close enough to be
mistaken for it:** client playbook edits land in a review state and merge only
on corporate approval (`actions.ts:195`, audit detail
`via: "client_edit_approval"` at `:225`). That is corporate approving a
client's data edit. This row is a client approving a corporate spend. Same
word, opposite direction, and no money in it.

**Spending authority exists only as free text**, in a Fernbrook demo playbook
field ("Sixty dollars per order without asking... above that Lisa approves").
A household fact in prose, not a limit the system can enforce or compare
against.

**One note for whoever scopes this:** an approval RECORD is not an invoice, so
this is buildable inside ADR-004's boundary. The app would capture the client's
yes; QuickBooks would still bill it.

### Row 6. Automated dunning: retry, notify, escalate on the Day 0/3/7/14/30 clock

**Verified: no.** Nothing. No payment retry, no reminder schedule, no
escalation ladder, and no payments layer for them to attach to.

**Worth separating two reasons it is absent**, because they have different
futures. The RETRY half is a processor behaviour and belongs to whichever
option D5 selects. The **notify and escalate** half is a schedule the app
could own under ADR-004 without originating a charge, and if it is ever built
it goes through `emitOutboxEvent` and the notification firewall like
everything else, not as a feature with its own send path.

### Row 8. Visit report with checklist, photos, and exceptions delivered to the client on completion

**Verified: partial. Delivery happens; the content is a subset.**

On visit close the client report email sends to `client.email`
(`api/visit-commands/route.ts:44-45`), and it ran in production on 27 August
with the three sentences, the photo count and correct escaping. So the
"delivered on completion" half is real and proven.

**The projection is `CLIENT_REPORT_KEYS = ["report", "photoCount"]`**
(`client-report.ts:24`). The client receives the HOM's three sentences and a
NUMBER OF PHOTOS. Not the photos. Not the checklist. Not exceptions as a
structured section.

**The exceptions exist and stop one screen short of the client.** The drafted
close composes "N of N expected outcomes completed as planned" plus itemized
exceptions, and renders it on the HOM's submit screen. It is not in the client
email.

**The row's own test is not traceable here.** It says the client-facing format
must "meet the QA five-dimension review". The five dimensions are in
WK-SOP-005 and the QA series, neither of which is in this repository.
**Delivery: partial, evidenced. Conformance: needs WK-SOP-005.**

### Row 9. Backup HOM assignment, coverage activation, and client notification of substitutions

**Verified: partial. Three clauses, three different answers.**

**Assignment: yes, and more than asked.** `backup_hm` is a first-class role
gating every field surface (`visit/page.tsx:28`, the visit-commands sink,
discard, mobile upload). Assignment and revocation go through audited actions
carrying ADR-006 subject tokens. Beyond the row: stranger mode gives a backup
the amplified first-visit projection (`visit/page.tsx:114-128`), which is the
substantive thing a covering HOM actually needs.

**Coverage activation: no, by boundary.** There is no scheduling in this
system; ADR-004 puts it in Jobber. A role assignment is not an activation, and
building one here would cross the boundary.

**Client notification of substitution: no.** Nothing notifies a member that a
different person is coming. The notification machinery exists and this is not
wired into it. Of the three clauses this is the one with no reason behind its
absence, and it is the one a member would notice.

### Row 10. Pause state: billing stopped, auto-resume on date, records preserved

**Verified: partial, and the middle clause is the sharp one.**

**Pause is a real, audited state change.** `pause` and `resume` are
`membership_event` kinds (`actions.ts:1119`), corporate_admin only, each
requiring an effective date, written in one transaction with the audit row.
They deliberately carry no tier and must not touch `household.tier`, asserted
in `actions.membership.test.ts:86`.

**Records preserved: yes.** Nothing hard-deletes; tombstone plus append-only
audit is the pattern throughout.

**Billing stopped: not represented, correctly.** There is no billing in this
app (ADR-004). The pause records that the state changed; money stops in
QuickBooks.

**Auto-resume on date: NO, and this is the row's real finding.** `resume` is a
second event a person records by hand. Nothing reads `effectiveOn` and fires.
An operator recording a pause with a future effective date could reasonably
believe she has scheduled the resume, and she has not. That gap is invisible
until the date passes and nothing happens.

### Row 11. Incident, near-miss, and feedback modules with categories and logs

**Verified: partial. Two of the three modules exist; the third does not.**

**Incident and near-miss: yes.** `incident_report` (`tables.ts:463-483`)
carries a kind enum of `complaint | breakage | injury | near_miss | other`
(`actions.ts:825`), severity, `occurredAt`, `reportedBy`, `reportedVia`,
a description, an open/resolved status with the resolution triple, and the
engine back-link (`preventableByPrompt`, `relatedRuleId`, `relatedPromptId`)
answered by whoever RESOLVES rather than inferred at creation. Categories and
logs, as asked.

**Feedback: no.** `complaint` is an incident kind, which is feedback only in
the sense that a fire is weather. There is no satisfaction capture, no
solicited feedback surface, and the brief for one is explicitly gated on 60
days of a real household.

**One word in the row is doing a lot of work.** Whether "feedback" means
solicited client satisfaction, unsolicited comment, or internal
continuous-improvement signal changes whether the answer is "no" or "no, and
deliberately so under the section 29 rule against a separate improvement form
where workflow data can generate the signal". **Needs WK-SOP-018 or -019.**

### Row 13. Client-visible billing history, itemized purchases, and pass-through detail

**Verified: no.** The client side has exactly one route, `(client)/playbook`.
`monthlyRateCents` renders only on corporate surfaces (the exhibit page and
`/oversight/economics`). No billing history, no itemization, no pass-through
detail reaches a member.

**Two reasons, and only one of them is a decision.** The client side is FROZEN
at the digest under WK-DEV-007, which is deliberate. And there is no billing
data to show, because payments do not exist. **D7 does not bar this row**:
D7 bars durations, service-hour totals and staffing ratios on client surfaces,
not money. A billing history is unbuilt and frozen, not prohibited.

### Row 14. Emergency contact one tap from every screen; driving mode deferring notifications

**Verified: no, on both clauses, and they fail differently.**

**Emergency contact: the DATA exists, the AFFORDANCE does not.** Emergency
contacts are playbook content in section 9, Safety and Emergency Readiness,
and the demo household carries several. Nothing puts them one tap from any
screen; there is no persistent control on any surface, web or native. A HOM in
a hurry would navigate to the playbook and read a field.

**Driving mode: nothing, and the row itself says why that may be right.** Its
interim names an OS-level driving focus mode on work profiles, which is a
device policy rather than software. Adjacent and NOT this: outbound
notifications are governed by a 9pm-to-7am rule under REQ-079's doctrine, which
is time-of-day, not motion.

## What the ten rows amount to

Stated because a row-by-row table hides it: **the pattern is not "unbuilt".**
Six of the ten have a working mechanism with a specific clause missing, and in
four of those the missing clause is the one a member or an operator would
actually notice: the substitution notice nobody sends (row 9), the resume
nobody schedules (row 10), the photos the client is counted but not shown
(row 8), the emergency contact that is data rather than a button (row 14).

Each of those is small. None is blocked by a boundary or a ruling. They are
the residue of building the record first and the moments around it later.

## The PAPER-PARITY acceptance test

**Its text is not in this repository.** Confirmed by search: zero matches for
`PAPER-PARITY`, `paper parity`, or `A228` anywhere in the tree, including
`docs/library/`.

The flag stands and is now sharper, because the trace has run. **Three of the
four ruled rows resolve to paper as the interim control**, and rows 5, 6, 13
and 14 have paper or manual answers behind them too. If the test asks whether
the software matches what the paper process does today, those rows pass by
definition, since the paper process IS the control. If it asks whether the
software can replace the paper, they all fail.

**That is not a close call between two readings; it is opposite verdicts on
roughly half the document.** Its text should be read before anything is
assessed against it.
